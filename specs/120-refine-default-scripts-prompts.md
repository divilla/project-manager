# Refine Default Scripts and Prompts

Types: refactor|migration|docs

## Goal

- Change creation uses one UUID identity across the API, backend service, repository, and database
  record, preserving a caller-supplied identity or generating one when the caller omits it.
- Default Flow scripts and prompts use shared default, temporary, Change, and stage paths without
  embedding workflow directory paths throughout the implementation.
- The CLI loads Change types once at startup, caches them for Go consumers, and publishes the
  ordered slugs as a shared prompt resource without prompts calling backend APIs.
- The repository workflow treats the PR code as the Change contract and keeps Specs and
  documentation aligned with accepted code behavior.

## Scope

- DB - Extend `fn_change_insert` to persist the resolved `_ref_uuid` with the new Change and keep
  demo seeding compatible with that four-argument contract.
- BE - Preserve caller-supplied `ref_uuid` values, generate missing identities, and carry the
  resolved value through repository persistence, responses, and tests.
- BE|CLI - Treat `Types:` metadata in Idea, Spec, and PR artifacts as an optional instruction and
  let the backend silently discard unsupported submitted type values.
- CLI - Remove the configurable temporary-directory contract, generate UUIDv7 Change identities,
  and create stage-scoped workspaces under `.mch/tmp` without changing existing Flow profile
  management, loading, validation, or read-only display behavior.
- CLI|SP - Load Change types once during CLI startup, expose the cached options to Go consumers,
  and rebuild the shared `prompts/change-types.md` catalog consumed by writing prompts.
- SP - Refine the default Makefile as an external Flow test harness together with Flow
  configuration, prompts, Codex session scripts, branch helpers, and promotion helpers already
  included in the prospective PR.
- SP - Use the new `prompts/spec-file-structure.md` contract throughout the default Flow.
- DOC|OTH - Align repository instructions and documentation with code and the PR as the source of
  truth for current behavior and technical contracts.

## Requirements

### Change creation identity

- DB - `fn_change_insert` accepts `_project_id`, `_ref_uuid`, `_title`, and `_idea` and inserts
  `_ref_uuid` into `public.change.ref_uuid`.
- DB - Change creation continues to insert the initial `idea` history row in the same transaction
  as the active Change row.
- DB - The unique `change_ref_uuid_index` continues to prevent two Changes from persisting the
  same `ref_uuid`.
- DB - The demo seed helper generates a UUID for each Change and passes it as `_ref_uuid` when
  calling the four-argument `fn_change_insert`.
- BE - `dto.ChangeCreateRequest` exposes optional `RefUUID` as the JSON field `ref_uuid`; an omitted
  field and explicit `null` both represent an absent caller identity.
- BE - Change create validation continues to require a valid project ID, non-blank title, and
  non-blank idea without requiring the caller to supply `ref_uuid`.
- BE - When `ref_uuid` is absent, the service generates a UUIDv7 before repository persistence.
- BE - When `ref_uuid` is supplied, the service preserves that exact UUID instead of generating a
  replacement.
- BE - A blank or malformed non-null `ref_uuid` fails request binding without creating a Change or
  its initial history.
- BE - The repository passes `ProjectID`, the resolved `RefUUID`, `Title`, and `Idea` to
  `fn_change_insert` in that order and preserves the existing transaction and refreshed-response
  behavior.
- BE - A successful create response returns the resolved `ref_uuid`, whether it was supplied by
  the caller or generated by the service.
- BE - Existing API clients that omit `ref_uuid` remain compatible and receive the generated value
  in the response.
- BE - `ref_uuid` is set only during Change creation. No update request or endpoint accepts it, and
  later mutations cannot replace or clear the persisted identity.
- BE - Change list, get, and later mutation responses continue to return the immutable persisted
  identity.

### CLI directories and Change workspace

- CLI - The CLI defines these shared directory constants:

```go
const (
	// pass to scripts as env var $MCH_DEFAULT_DIR
    DefaultDir = ".mch/default"

    // pass to scripts as env var $MCH_TEMP_DIR
    TempDir = ".mch/tmp"
)
```

- CLI - `.mch/config.yaml` no longer defines `temp_dir`, and CLI configuration loading, saving, and
  rendering do not read, require, persist, or display that key.
- CLI - A legacy `temp_dir` key has no effect when present; the CLI does not consult or migrate
  files from a previously configured temporary path.
- CLI - The runtime temporary root is always `TempDir` resolved relative to the Git repository
  root, never a system temporary directory or configuration-provided path.
- CLI - Removing `temp_dir` does not change the existing `backend_url` and `project_id`
  configuration contracts.
- CLI - Existing Flow profile management, loading, validation, and read-only rendering remain
  unchanged.
- CLI - The CLI continues to treat configured `entry`, `exec`, and `exit` hook strings as read-only
  metadata and does not launch Flow scripts, hook commands, or default Makefile targets.
- CLI - Every external process launched by the CLI for Idea, Spec, or PR writing inherits the
  caller environment with `MCH_DEFAULT_DIR=DefaultDir`, `MCH_TEMP_DIR=TempDir`, the Change identity
  as `MCH_REF_UUID`, and `MCH_STAGE=idea`, overriding inherited values with those names.
- CLI - Artifact-writing environment values do not come from Flow profile state. Directory values
  come from constants, `MCH_REF_UUID` comes from the created or reloaded Change, and `MCH_STAGE`
  remains fixed to `idea` for `idea-write`, `spec-write`, and `pr-write`.
- CLI - An external process is not launched until its Change UUID and idea workspace are
  available; a command failure stops the active artifact action and is not reported as success.
- SP - Default Makefile commands remain externally or manually invoked for Flow testing; their
  caller supplies the same four required environment values before running a target.
- CLI|SP - Default and temporary paths under `.mch` and `cli` are derived from the shared
  constants or environment instead of repeated `.mch/default`, `/default`, `.mch/tmp`, or `/tmp`
  workflow path literals.
- CLI - New Change creation uses `github.com/gofrs/uuid/v5` to generate a UUIDv7.
- CLI - The generated UUID is used as both the create request `ref_uuid` and the directory name
  under `.mch/tmp`.

### Startup Change type catalog

- CLI - The startup option-catalog command is the only CLI runtime caller of
  `POST /api/v1/options/change-types-list`; later selectors and filters reuse startup-loaded
  options without another type-catalog request.
- CLI - After a successful startup type load, the CLI overwrites
  `.mch/default/prompts/change-types.md` in backend order with exactly one `# Change Types` H1, one
  blank line, and one `- <slug>` Markdown list item per returned option, ending with a newline.
- CLI - The CLI writes the Change type prompt resource but never reads it. A missing file is
  created when its prompt directory exists, and stale file content is replaced completely.
- CLI - The exported `app.ChangeTypes()` function returns a defensive copy of the Change type
  options cached during startup so callers cannot mutate shared cached state.
- CLI - A failed type-catalog request leaves the existing prompt file and cache unchanged. The
  prompt is replaced atomically only after its temporary sibling is written and closed; any file
  write failure preserves the previous prompt, reports the existing option-catalog startup error,
  and does not replace the cache.
- CLI - Change feature interfaces do not expose type-catalog loading; the startup app layer owns
  that operation.

#### `/new-change` sequence

1. CLI - Generate one UUIDv7 before opening the editor.
2. CLI - Create `TempDir/<generated-ref-uuid>/idea` beneath the Git repository root.
3. CLI - Create blank `input.md` and `output.md` files in that `idea` directory.
4. CLI - Open the editor on `output.md`; `input.md` remains the unchanged blank comparison
   baseline.
5. CLI - After the editor exits, compare `input.md` and `output.md` byte for byte.
   - When they differ, show `Create Change?` with Yes and No choices without validating the
     artifact first.
   - No cancels creation, removes the generated UUID workspace, and returns to
     `ChangesListScreen` without calling the create API.
   - Yes re-reads `output.md` and validates that it has a non-blank `# <title>` H1 and non-blank
     Idea content after the optional `Types:` metadata. Validation failure opens `ErrorScreen`,
     preserves both files, and does not call the create API.
   - After successful validation, process an included `Types:` value through the shared Idea,
     Spec, and PR artifact type contract below, then call `POST /api/v1/change/create` with
     `project_id`, the generated UUID as `ref_uuid`, the parsed `title`, and the complete content
     as `idea`. The metadata line remains part of the complete artifact text.
   - `Epic:` has no metadata meaning in Idea, Spec, or PR artifacts: the CLI does not generate,
     extract, validate, or persist it from those artifacts. Users attach an epic after creation
     through the Change details epic selector.
   - After creation provides a Change ID, an included `Types:` line always causes a
     `POST /api/v1/change/update-change-types` request, including when its parsed value is an empty
     array. The CLI uses the complete Change returned by that update; an omitted `Types:` line
     sends no type update.
   - The successful create response is the persistence boundary. The CLI immediately stores the
     returned Change and routes to `ChangeDetailsState` before running any post-create file or type
     operation. No later recovery action may call create again for that Change UUID.
   - After successful creation, copy `output.md` over `input.md`, keep the UUID workspace, and enter
     the existing `RewriteIdeaState`.
   - If `output.md` changes or disappears after the create request has been accepted and the
     post-create copy fails, or the post-create type update fails, the persisted-Change error flow
     offers `/fix` and `/cancel` from `ChangeDetailsState`. `/fix` edits and updates the existing
     Change; leaving the reopened output unchanged and `/cancel` both return to
     `ChangeDetailsState` without another create request or workspace removal.
   - The rewrite reads `input.md`, writes the rewritten Idea to `output.md`, saves that complete
     output through the existing agent-edit Idea update, reloads the created Change, and opens
     `ChangeDetailsScreen`.
   - A create API failure opens `ErrorScreen`, preserves both files, and does not present the
     Change as created. A failure after create succeeds presents the returned Change in
     `ChangeDetailsState` and uses persisted-Change recovery.
   - `ErrorScreen` offers `/fix` and `/cancel`, with `/fix` selected by default.
   - `/fix` copies `output.md` over `input.md` in the same UUID workspace and returns to step 4 to
     reopen the editor on `output.md`.
   - There is no unchanged retry action. `/fix` requires another editor pass, and leaving
     `output.md` unchanged follows the equal-file cancellation in step 6.
   - `/cancel` removes the complete `TempDir/<generated-ref-uuid>` workspace and returns to
     `ChangesListScreen` without calling the create API again.
6. CLI - When the files are equal, cancel creation, remove the generated UUID workspace, and return
   to `ChangesListScreen` without calling the create API.

- CLI - UUID generation, directory creation, or file creation failure stops before the editor and
  create API call, removes any partial workspace created for that UUID, and reports the failure.
- CLI - Loading, editing, resuming, or running a stage for an existing Change never invokes the
  `/new-change` initializer or truncates existing workspace files.

#### Existing Change artifact-write sequence

1. CLI - Reload the selected Change and require its persisted `ref_uuid` before opening an Idea,
   Spec, or PR editor.
2. CLI - Create `.mch/tmp/<ref_uuid>/idea` when absent without invoking the new-Change initializer,
   removing existing files, or replacing its saved Codex session.
3. CLI - Select `idea-write`, `spec-write`, or `pr-write` from the artifact being edited while
   keeping `MCH_STAGE=idea` for every operation.
4. CLI - Write the reloaded backend artifact text to `idea/output.md`, copy it to `idea/input.md`,
   and open the editor on `idea/output.md`.
5. CLI - An unchanged editor exit keeps the workspace and returns to `ChangeDetailsState` without
   an artifact or type update.
6. CLI - Changed output is saved through the matching Idea, Spec, or PR endpoint with
   `agent_edit=false`; present `Types:` metadata is applied, the Change is reloaded, and the saved
   `idea/output.md` is copied to `idea/input.md`.
7. CLI - Run the selected artifact-write prompt in the same idea workspace and saved session, save
   its complete `output.md` through the same endpoint with `agent_edit=true`, apply present types,
   reload the Change, and return to `ChangeDetailsState`.

### Idea, Spec, and PR type metadata

- CLI - Idea, Spec, and PR artifact processing uses one three-state `Types:` contract:
  - When `Types:` is omitted, do not call `POST /api/v1/change/update-change-types` and leave the
    Change's existing types unchanged.
  - When `Types:` is present with an empty value, call
    `POST /api/v1/change/update-change-types` with an empty string array.
  - When `Types:` is present with a non-empty value, treat pipes and whitespace as separators,
    remove every `[^A-Za-z\-_]` character from each resulting value, discard empty values, and
    submit that string array to `POST /api/v1/change/update-change-types`.
- CLI - For an existing Change artifact save, after every
  `POST /api/v1/change/update-change-types` succeeds, call `POST /api/v1/change/get` and use that
  response as the current Change. Initial Change creation instead uses the complete Change returned
  by its post-create type update. This applies equally to empty and non-empty submitted arrays.
  Only an omitted `Types:` line skips the type-update call.
- CLI - Artifact type processing does not call `POST /api/v1/options/change-types-list`, does not
  reject unsupported type strings, and does not modify the `Types:` text stored in the artifact.
- BE - `POST /api/v1/change/update-change-types` accepts any client-supplied string array, filters
  it against the type values currently available in the backend, silently removes every
  unsupported value, and replaces the Change's complete type set with the filtered array,
  including an empty result.
- BE - Unsupported submitted type values never produce a validation error. Clients do not need to
  prevalidate artifact-derived values against the options endpoint.
- CLI - The same three-state processing runs for the final reread immediately before creating an
  Idea and whenever an Idea, Spec, or PR artifact is saved, regardless of whether the artifact was
  produced by a user or an agent.

### Workspace stages

- CLI - `MCH_STAGE` is hardcoded to `idea` for every CLI-launched process in this Change. Artifact
  kind selects the write operation and endpoint, never a different workspace stage.
- SP - The stage contract and mapping below apply only to externally or manually invoked default
  Flow targets whose caller supplies `MCH_STAGE`.
- SP - `MCH_STAGE` uses exactly `idea`, `spec`, `spec-review`, `docs`, `code`, `pr`,
  `code-review`, `code-docs`, or `merge`.
- SP - Existing default Flow steps map to workspace stages as follows:

| Flow step | `MCH_STAGE` |
| --- | --- |
| `idea-write`, `idea-review`, `idea-chat`, `spec-write`, `pr-write` | `idea` |
| `spec-review`, `spec-review-chat` | `spec-review` |

- SP - The stage mapping defines workspace context only; it does not create an automatic
  transition or execution sequence between Flow steps.
- SP - All steps for one Change reuse its `MCH_REF_UUID` while keeping each stage's files and
  Codex session inside that stage directory.
- SP - `spec-write` is an Idea-to-Spec transition helper that uses `MCH_STAGE=idea`, so Spec
  writing remains attached to the existing Idea workspace and Codex session.
- SP - `spec-write` requires the current Idea at `idea/output.md`, copies that file over
  `idea/input.md`, and supplies `idea/input.md` as the Spec-writing prompt input. The generated
  Spec replaces `idea/output.md`; the output artifact type does not move the session out of the
  `idea` stage.
- SP - `spec-write` does not prepare or restore a missing Idea artifact from the branch. Missing
  `idea/output.md` is an invalid transition state and fails before Codex starts.
- SP - `pr-write` also uses the `idea` workspace and session; the output artifact does not select
  the `pr` workspace stage.
- SP - `spec-review` and every `spec-review-*` helper use `MCH_STAGE=spec-review`. Spec review
  starts from the branch Spec copied into the `spec-review` workspace, and review chat resumes
  the session stored in that workspace.
- SP - The legacy `spec-exec` and `ready-exec` Make entry points do not exist; invoking either
  target fails without running a Flow script.
- SP - Scripts reject missing required environment values, invalid UUID text, unsafe relative
  directory values, missing stage resources, and unknown saved Codex sessions before execution.

### Default scripts and prompts

- SP - The default Makefile is an external test and manual-execution harness, not a CLI runtime
  dependency.
- SP - The default Makefile builds its temporary path from `MCH_TEMP_DIR`, `MCH_REF_UUID`, and
  `MCH_STAGE` and requires all three values before preparing artifacts.
- SP - Idea preparation copies the branch Idea into `idea/output.md` only when the invoking
  workflow explicitly requests preparation. Idea initialization copies the existing
  `idea/output.md` over `idea/input.md` before rewrite, review, or Spec generation.
- SP - The default Flow references the refined prompt names for Idea rewriting and review and for
  Spec writing and review.
- SP - Every configured prompt and utility prompt path resolves to an existing prompt file; no
  active Flow entry references a removed legacy prompt.
- SP - Prompt rendering replaces `/stg-tmp-dir/` with the active stage directory and `/def-dir/`
  with `MCH_DEFAULT_DIR` in new, restored, exec, and interactive session paths.
- SP - `spec-write.md` loads `/def-dir/prompts/change-types.md`, requires its `# Change Types`
  heading and `- <slug>` entries, selects only listed slugs, and always writes a populated
  `Types:` line in a newly generated Spec.
- SP - `spec-file-structure.md` treats `Types:` as optional and validates only its placement and
  pipe-delimited syntax. Omitted, explicitly empty, and populated metadata are structurally valid
  without loading or validating against a type catalog.
- SP - Prompt Markdown never instructs an agent to call a backend API. Prompts that select Change
  types read the generated catalog file; structural, review, implementation, documentation, and
  reconciliation prompts do not load type options.
- SP - Session scripts use `session-id`, `agent-output.md`, `events.jsonl`, and `error.log` inside
  the active stage directory.
- SP - Restore execution resumes a known session when possible and starts a new session when the
  saved session is absent or unavailable.
- SP - Restore execution streams Codex events to `events.jsonl`, preserves command failures, and
  writes a final agent output artifact.
- SP - Interactive progress identifies a started or restored session, shows elapsed `MM:SS`, and
  advances event dots with a pulse while Codex runs.
- SP - The `spec-review-chat` Make target externally tests interactive resume in the `spec-review`
  workspace without defining how the CLI invokes that script.
- SP - The repository retains the applied helpers for Change slug extraction, Change branch
  initialization, environment export, and guarded promotion from `stage` to `master`.
- SP - A Change slug is valid if and only if it matches `^[0-9]+-[0-9A-Za-z_-]+$`; every validator
  applies that exact grammar, and every branch extractor applies
  `^change/([0-9]+-[0-9A-Za-z_-]+)$` to the complete branch name.
- SP - Branch initialization rejects invalid slugs, dirty worktrees, and conflicting local or
  remote branches for the same numeric Change reference.
- SP - Master promotion runs only from a clean `stage` branch, verifies remote heads and ancestry,
  and refuses stale or unsafe promotion.

### Spec and documentation contract

- SP - `prompts/spec-file-structure.md` defines the top-level Spec sections in this exact order:
  `Goal`, `Scope`, `Requirements`, `Non-Goals`, `Design Notes`, `Verification`, `QA Test Cases`,
  `Review Focus`, and `Follow-Ups`.
- SP - Artifact templates and consumers treat `Types:` as optional in Idea, Spec, and PR Markdown;
  omission is a no-op rather than a structural validation failure.
- SP - Spec-writing and Spec-review prompts inspect the Idea, full branch state, relevant tests,
  documentation, and PR metadata when available before producing or reviewing a Spec.
- SP - Idea rewrite and review prompts preserve the latest draft in stage artifacts and keep
  review output separate from the Idea document.
- SP - Implementation, review, fix, documentation, and PR prompts use the Spec as requested scope
  while treating code and the published PR as authoritative accepted behavior.
- OTH - `AGENTS.md` keeps the PR as the de facto Change and uses the complete branch diff as the
  provisional contract before publication.
- DOC - Documentation describes code as the source of truth for current behavior and technical
  contracts and must be corrected when stale.
- DOC|CLI - CLI architecture and verification documentation remove the configured `temp_dir`
  contract and describe `.mch/tmp` as the repository-relative runtime workspace root.
- DOC - Documentation uses Requirements and QA Test Cases without requiring a separate top-level
  Acceptance Criteria section.
- DOC - Existing documentation stays within the repository's 300-line-per-file limit.

## Non-Goals

- Adding a new `ref_uuid` column or foreign key; the existing column and unique index remain.
- Changing project-scoped `ref`, `slug`, Flow assignment, or Run-state ownership.
- All frontend code, tests, API-client changes, workflows, and presentation behavior; the frontend
  is entirely out of scope.
- Changing CLI Flow profile management, loading, validation, or read-only rendering, or adding CLI
  execution of Flow scripts, configured `entry`, `exec`, and `exit` hooks, or default Make targets.
- Deriving CLI `MCH_STAGE` from the active Flow step or launching CLI external processes for stages
  other than `idea`; those integrations require later Changes.
- Adding a separate `init-idea-file.sh`; Idea artifact preparation remains in the documented
  Makefile and CLI paths.
- Implementing the broader Flow redesign described in `agent/ideas/187-cli-flow-architecture.md`.
- Adding project-wide locking, advisory locking, or stronger transaction isolation.
- Adding dedicated recovery for `output.md` changing or disappearing between an accepted create
  request and the immediately following copy to `input.md`.

## Design Notes

### Identity and persistence

- The CLI owns UUIDv7 generation for the Change Flow introduced here. Other API clients may omit
  the identity, in which case the backend service generates UUIDv7 before persistence through
  `fn_change_insert`.
- The existing simple transaction pattern remains: begin, defer rollback, insert, refresh, and
  commit.
- Request binding rejects malformed non-null UUID values. The database UUID type and unique index
  remain the persistence boundary for resolved and duplicate identities.
- The resolved `ref_uuid` is immutable after creation. Later API contracts expose it as response
  data only and provide no operation that can update it.

### Workspace model

- `MCH_TEMP_DIR` is the Flow temporary root, `MCH_REF_UUID` identifies one Change, and
  `MCH_STAGE` isolates the active stage's files and session.
- A workspace stage identifies the source context and Codex session being continued, not the
  artifact type that a prompt will produce. Consequently, Spec writing consumes and replaces
  artifacts in the `idea` workspace, while Spec review owns a separate `spec-review` workspace.
- `MCH_TEMP_DIR` always receives `.mch/tmp`; `.mch/config.yaml` does not override the workspace
  location.
- CLI workspace initialization is a new-Change creation bootstrap only, not a general stage-entry
  operation. Existing artifact edits create missing directories idempotently, refresh only
  `input.md` and `output.md` from backend text, and preserve the saved session and logs.
- `input.md` is the immutable baseline for one `/new-change` editor pass, while the editor writes
  only `output.md`. A byte-for-byte equality check is sufficient because both files start empty.
  After the create API succeeds, `output.md` becomes the rewrite source by overwriting `input.md`.
- Idea, Spec, and PR artifacts may omit `Types:`. When present, even with no value, the metadata
  line remains inside the complete artifact Markdown while its parsed array drives a complete
  backend type replacement. Existing-Change saves then reload details; initial creation uses the
  Change returned by the type update.
- Idea, Spec, and PR artifacts do not carry Epic metadata. Epic assignment remains a separate
  post-creation Change details action.
- Artifact parsing deliberately does not depend on the type options catalog. The backend owns the
  supported-type intersection so stale or unknown artifact values are harmless and disappear from
  the persisted type array without an error.
- A no-op editor pass and a No response to `Create Change?` have no durable Change or workspace.
  Validation and create API failures retain the UUID workspace while `ErrorScreen` is active.
  Before persistence, `/fix` makes the current output the next editor baseline and `/cancel`
  removes the whole UUID workspace. Successful Change creation keeps the workspace for later Flow
  stages and changes recovery semantics to existing-Change editing and details navigation.
- The create command re-reads and parses `output.md` immediately before persistence. A later
  post-create copy or type-update failure uses persisted-Change recovery: `/fix` updates the
  existing Change, while unchanged editor exit and `/cancel` retain the workspace and return to
  Change details without another create request.
- The stage mapping table is the smallest useful visualization for the many-to-one relationship
  between configured Flow steps and workspace directories; a separate diagram would duplicate it.
- Default and temporary directory environment values are repository-relative and must not be
  absolute or contain `..` path traversal.

### Workflow contract

- CLI program integration tests enter through the complete Bubble Tea program boundary with a
  temporary repository config, controlled key input and rendered output, a subprocess-backed fake
  editor, an HTTP test backend, and an injected agent runner. They do not call model workflow
  helpers or synthesize completion messages directly.
- Flow hook commands are configuration displayed by the CLI and invoked externally or manually;
  this Change does not add automatic hook execution, cross-stage sequencing, or output promotion.
- External callers supply the Flow environment and mapped stage consumed by the default Makefile
  and scripts. The CLI does not execute those Flow rules; its artifact-write environment
  is assembled directly from the shared constants, created or reloaded Change UUID, and hardcoded
  `idea` stage.
- Prompt filenames describe their workflow purpose, while prompt front matter may retain existing
  `change-*` names where those names identify the agent behavior.
- The canonical Change slug validation grammar is `^[0-9]+-[0-9A-Za-z_-]+$`; `change/` is the
  branch namespace prefix and is not part of the slug. Full-branch extraction uses
  `^change/([0-9]+-[0-9A-Za-z_-]+)$` everywhere.
- The canonical Spec structure is `.mch/default/prompts/spec-file-structure.md`.
- `.mch/default/prompts/change-types.md` is a CLI-generated prompt input and committed baseline.
  The CLI owns its startup refresh and in-memory cache; prompts own reading it, and the structure
  template deliberately remains independent of the current catalog.
- Relevant current contracts are documented in `docs/docs-rules.md`,
  `docs/architecture/backend-api.md`, `docs/architecture/cli.md`, `docs/architecture/mch.md`,
  `docs/functionality/change-lifecycle.md`, `docs/operations/verification.md`,
  `docs/functionality/pr-integration.md`, and `docs/functionality/requirements-and-acceptance.md`.

## QA Test Cases

- BE|DB - Create a Change with a valid UUIDv7 and verify create, list, and get return that exact
  `ref_uuid` while the initial idea history is created.
- BE|DB - Create Changes with omitted and explicit `null` `ref_uuid` values and verify each response
  returns a generated UUIDv7 that persists unchanged through list and get.
- BE|DB - Submit blank and malformed non-null `ref_uuid` values and verify each request fails
  without creating a Change or history row.
- BE|DB - Submit a duplicate `ref_uuid` and verify the second create fails without replacing the
  existing Change.
- DB - Load the demo seed after `db/init.sql` and verify all demo Changes are created with non-null,
  unique `ref_uuid` values through the four-argument `fn_change_insert`.
- BE - Perform every supported later Change mutation and verify no request accepts `ref_uuid` and
  the created identity remains unchanged in subsequent responses.
- CLI - Start from a repository config containing only `backend_url` and `project_id` and verify the
  CLI loads successfully without requiring `temp_dir`.
- CLI - Start with stale `prompts/change-types.md` content and a controlled ordered backend type
