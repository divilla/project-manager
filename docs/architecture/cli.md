# CLI

## Purpose
`cli/` is the repository directory for terminal-facing tools. Today it contains the `mch` Bubble Tea terminal UI, so references to the "CLI module" in this repository usually mean the interactive TUI application rather than a broad subcommand-oriented automation CLI.

Future non-interactive CLI commands may be added for developers and agents. They should expose stable commands for project context, change workflow, and local verification without bypassing backend rules.

## Design Direction
The CLI should call supported backend APIs or documented local commands. It should not write application tables directly unless a command is explicitly an operations command and is documented as such.

## Prototype
The `cli-proto/` directory may contain experimental terminal prototypes. The first prototype binary is `mch`, a Bubble Tea app for Codex-assisted Change test case planning. It starts without subcommands, accepts only `--backend-url`, resolves the current Git repository root with `git rev-parse --show-toplevel`, and uses that root for prompt lookup and Codex execution.

The prototype stores its local config under `cli-proto/.config`. It may persist backend URL and current project selection there, but it must save product data only through supported backend APIs.

## Reference TUI
The `cli/` module contains the reference `mch` TUI. Its architecture, package boundaries, style tokens, state model, and test strategy are documented in `docs/architecture/mch.md`. The executable remains `mch`; `cli/` is only the source directory name.

`mch` owns the interactive `/new-change` flow from the Change list. It generates one UUIDv7, creates `.mch/tmp/<ref-uuid>/idea` with blank `input.md` and `output.md`, then opens the editor on `output.md`. After the editor exits, it compares the files byte for byte. Equal files cancel creation, remove the generated UUID workspace, and return to `ChangesListScreen` without an API call. Changed output shows `Create Change?` without artifact validation. No removes the workspace and returns to the list without a request. Yes re-reads `output.md`, requires a non-blank H1 title and non-metadata Idea body, and only then sends `project_id`, generated `ref_uuid`, parsed title, and the complete output as `idea` to `POST /api/v1/change/create`. `Types:` is optional and unsupported values do not invalidate an artifact. `Epic:` has no metadata meaning in Idea, Spec, or PR artifacts and is not extracted or validated; Epic assignment remains available after creation through the Change details `/epic` selector. Validation errors retain both files for correction and send no request. A successful create response immediately becomes the current Change in `ChangeDetailsState`. Present `Types:` metadata then causes a separate `POST /api/v1/change/update-change-types` request, including for an empty array, and the CLI uses the complete Change returned by that update; omitted metadata sends no type update. Create API errors retain the workspace for retry and do not present a Change. Create success copies `output.md` over `input.md` and enters the existing rewrite flow, which reloads the rewritten Change before opening its details. If that copy or the post-create type update fails, recovery remains anchored to the persisted Change: `/fix` edits and updates it, while unchanged editor exit and `/cancel` retain the workspace and return to `ChangeDetailsState` without another create request. Partial workspace initialization is removed before reporting an initialization failure. Existing-Change operations never invoke this initializer or truncate its files.

Editing an existing Idea, Spec, or PR first reloads the Change and uses its persisted `ref_uuid` to open `.mch/tmp/<ref-uuid>/idea`. Missing directories are created idempotently; the new-Change initializer is not used. The backend artifact is written to `output.md` and copied to `input.md` before the editor opens, while `session-id`, logs, and other stage files are preserved. Unchanged output returns to Change details without an update. Changed output is saved with `agent_edit=false`, applies present `Types:` metadata, reloads the Change, and is copied from `output.md` to `input.md` before `idea-write`, `spec-write`, or `pr-write` starts. All three operations use `MCH_STAGE=idea` and the same saved session. Agent output is saved through the matching artifact endpoint with `agent_edit=true`, types are applied when present, and the Change is reloaded before details reopen. `/edit-spec` uses this same Spec artifact-write path.

Idea, Spec, and PR saves use the same three-state type metadata handling. Omitted `Types:` means no type update. A present `Types:` line always calls `POST /api/v1/change/update-change-types`: an empty value sends an empty array, while a non-empty value treats pipes and whitespace as separators, then removes every `[^A-Za-z\-_]` character from each value and discards empty values. The CLI does not fetch type options or reject unsupported values for artifact processing. The backend filters the array against available types, silently drops unsupported values, and replaces the Change's complete type set. After the update succeeds, the CLI reloads the Change through `POST /api/v1/change/get` and uses the returned types.

At application startup, `mch` loads Change type options once, keeps them in its option catalog, exposes a defensive copy through `app.ChangeTypes()`, and rewrites `.mch/default/prompts/change-types.md` in backend order. The generated Markdown contains `# Change Types`, one blank line, and one `- <slug>` item per option. It is written and closed as a temporary sibling before atomically replacing the previous catalog. The CLI only writes this prompt resource; prompts read it when they need semantic type selection. Later CLI selectors reuse startup-loaded options and do not reload the type catalog.

`mch` resolves the current Git repository root before loading configuration, so starting from the root or a nested directory uses the same `.mch` tree. `.mch/config.yaml` owns `backend_url` and `project_id`; `temp_dir` is not a configurable field, and runtime workspaces always use repository-relative `.mch/tmp`. The Main screen includes `/config`, which opens a read-only view of resolved in-memory CLI and Flow configuration without calling backend APIs, reading raw YAML for rendering, executing hooks, or saving local files.

Flow profile management, loading, validation, and read-only display remain configuration concerns. The CLI does not execute configured `entry`, `exec`, or `exit` hooks or default Makefile targets. External artifact-write processes receive `MCH_DEFAULT_DIR=.mch/default`, `MCH_TEMP_DIR=.mch/tmp`, the created or reloaded Change UUID as `MCH_REF_UUID`, and `MCH_STAGE=idea`, overriding inherited values with those names. These values come from CLI constants and Change state without consulting Flow profile data. Flow-derived stage selection and CLI external-process execution outside the `idea` workspace remain future work.

Repository Change workflow automation uses `change/<change-slug>` branches, ideas under `agent/ideas/<change-slug>.md`, and Change specs under `specs/<change-slug>.md`. The spec structure template is `.mch/default/prompts/spec-file-structure.md`. This does not rename application routes, API paths, packages, or product data that use the Change concept.

`spec-write.md` reads the generated Change type catalog and uses only listed slugs when producing a populated `Types:` line. `spec-file-structure.md` treats `Types:` as optional and validates only placement and pipe-delimited formatting, so later prompts can validate structure without loading a catalog. Prompt Markdown does not call backend APIs.

## Current Project
For `mch`, current project selection is committed repository and branch configuration stored as numeric `project_id` in `.mch/config.yaml`. Missing `project_id` and `project_id: 0` mean no current project is selected. CLI commands that operate on project-scoped data must use a valid configured project ID or require an explicit project option.

## Agent Use
Agents can use CLI commands when commands are deterministic, documented, and return structured output. Prefer JSON output for commands intended for automation.

## Boundaries
The CLI must not become a parallel product implementation. Product rules remain owned by backend services, database constraints, and documented workflows.
